**Short answer:** yes, every requirement was met with Astryx components alone, with no accessibility violations found. The cost is weight (about 463 kB of compressed JavaScript on first load) and commitment to a beta system with its own layout vocabulary.

The task every UI library study builds is specified in [`docs/comparisons/ui-library-task.md`](../../../docs/comparisons/ui-library-task.md). Results across libraries are in [`docs/comparisons/component-libraries.md`](../../../docs/comparisons/component-libraries.md).

## What was built

The inventory admin screen: side navigation, a 42-row table with sorting, selection, bulk delete and pagination, search and two filters with an empty state, a create/edit dialog with validation, delete confirmation with an undo toast, a loading skeleton, light/dark mode and a custom brand theme.

```
app/
  layout.tsx, providers.tsx   Theme, LinkProvider, ToastViewport, brand theme
  globals.css                 two Astryx imports and one height rule
  page.tsx                    the test screen
  template/                   scaffolded Astryx template + a wrapper layout
  about/                      requirement-to-component map
components/
  app-frame.tsx               AppShell + SideNav + appearance controls
  inventory-screen.tsx        table, filters, toasts, delete confirmation
  item-dialog.tsx             create/edit form
lib/inventory.ts              data, types, validation (shared shape for all UI studies)
astryx-themes.ts              generated by `astryx theme add`
AGENTS.md, GEMINI.md          generated by `astryx init` and `next dev`
```

## Results against the shared criteria

| Criterion | Result |
|---|---|
| **Coverage** | 8 of 8 requirements with library components alone |
| **Custom code** | 0 custom components, 0 raw HTML elements, 0 `className`/`style` props in 702 lines of screen code. 10 lines of CSS, 8 of them comments and imports |
| **Accessibility** | axe-core, WCAG 2.2 A/AA rules: 0 violations in 6 states (table in light, dark, brand theme and at 390px; dialog with errors; empty state). Keyboard-only pass succeeded, with two notes below |
| **JavaScript shipped** | `/`: 463 kB compressed (1.41 MB raw) in the initial HTML, plus 118 kB prefetched for the other routes. For scale, a page of the Tempo study on the same Next.js version ships 169 kB |
| **CSS shipped** | 50 kB compressed, plus one 20 kB font file |
| **Setup** | 4 packages, 2 CSS imports, `astryx theme add`, 3 providers. No bundler plugin on the plain-CSS path |
| **Theming** | Dark mode is one prop (`mode`). The brand theme is 8 lines: `defineTheme({ extends, tokens })` with `[light, dark]` colour pairs |
| **Documentation** | Sufficient on its own. Every prop taken from the CLI docs type-checked on the first compile |
| **Upgrade path** | Bump all `@astryxdesign/*` packages together, then run `astryx upgrade --from <old> --apply` (a codemod step). Themes pin an exact core version |
| **Maturity** | 0.7.13, beta. MIT. Maintained by Meta at `meta/astryx`, pushed to daily at the time of the study |

A scripted behaviour pass (28 checks covering all eight requirements) passes on the production build with an empty browser console.

## Findings

**What works well**

- **The table is the strongest part.** Sorting, selection, pagination and filtering are separate plugins passed to one `<Table>`, each with a state hook. Combining three took about 25 lines, and paging exposes `aria-rowindex`/`aria-rowcount` when you pass two props.
- **Accessibility arrives without being asked for.** Toasts and the empty state are announced through a polite live region, invalid fields get `aria-invalid`, the delete confirmation is a real `alertdialog`, focus is trapped in dialogs and returns to the trigger, and status dots require a text label.
- **The app frame is one component.** `AppShell` owns the regions and scroll containers and turns the side navigation into a drawer on small screens. No media query was written.
- **The documentation lives in the CLI and matches the installed version.** `npx astryx component <Name>` prints props, do/don't rules and theming hooks; `npx astryx template <Block>` prints working source.
- **Setup worked unchanged with Next.js 16, Turbopack and Cache Components.**

**What to know before adopting it**

- **It is heavy.** 463 kB of compressed JavaScript before any of your own features. Per-component import paths did not keep this small: the `/about` page, which uses only a table and the frame, still loads 425 kB.
- **The intended workflow is template-first.** `astryx build "<idea>"` recommends a page template, and the generated `AGENTS.md` tells coding agents to start from one. `table-page` scaffolded as a single 992-line file, about 180 lines of it design guidance in comments, and it ran unmodified. Some templates use StyleX and then do need a compiler plugin (`@stylexswc/nextjs-plugin` for Next.js).
- **You adopt its layout vocabulary.** Layout is `VStack`, `HStack`, `Layout` and spacing-scale numbers, not CSS. That is why no CSS was needed, and also why leaving Astryx later means rewriting layout, not just swapping components.
- **`hasAutoFocus` inside a `Dialog` breaks focus return.** With it, closing the dialog dropped focus on `<body>`. Without it, focus returns to the trigger. The dialog puts initial focus on its title either way, so the prop gains nothing there.
- **Escape on a focused icon button closes its tooltip first.** From the dialog's Close button the dialog needs a second Escape. From anywhere else one press closes it.
- **Row types must extend `Record<string, unknown>`.** That index signature makes `Omit<Row, "id">` turn every field into `unknown`. Keep a plain base type and intersect it for the table (see `lib/inventory.ts`).
- **A runtime theme logs a warning in development.** `defineTheme()` at runtime injects styles; Astryx recommends a pre-built theme package for production.
- **The table does not reflow on small screens.** At 390px it scrolls sideways inside its own container. The page itself does not overflow, but there is no built-in card or stacked layout for narrow widths.
- **Its own rules and examples disagree in places.** The generated `AGENTS.md` says "No `<div>`", while the official `TableBulkActionsTable` block wraps its content in one.

## Verdict

- **Use it when:** you are building data-heavy internal tools or dashboards on React 19, want accessibility and consistency by default, and are willing to build the whole interface in one system. It is especially strong where tables, filters and forms dominate, and where coding agents will write much of the UI.
- **Avoid it when:** first-load size matters (public marketing or commerce pages, slow phones), you need a distinctive visual identity beyond tokens, you are not on React 19, or you cannot accept beta churn with codemods between releases.
- **Cost:** about 300 kB more compressed JavaScript than a comparable page without it; lock-in to its layout components; a beta API.
